# Releasing wardenrun

The runbook for the maintainer. A release is a tag: pushing `vX.Y.Z` starts
[`.github/workflows/release.yml`](../.github/workflows/release.yml), which tests, signs,
verifies, attests and publishes, then updates the Homebrew tap and installs from it as a last
check. Nothing in this file is needed to *use* wardenrun.

> **No release has been cut yet.** Sections 1 and 3 have to be done once, by hand, on a real
> Mac, before the first tag. The pipeline's scripts were checked by the CI dry run
> (`scripts/ci-release-dry-run.sh`, a throw-away certificate) but the workflow itself has never
> run: the first tag is its first real run.

## 1. One-time: the signing certificate

The certificate is generated by the maintainer, on the maintainer's own Mac, and never by CI,
an assistant or anybody else. Its SHA-1 becomes the identity every user's keychain item is
bound to, so treat the private key like the key of a package registry.

Work in a folder that is **not** inside the repository, with a restrictive umask:

```sh
mkdir -p ~/wardenrun-signing && cd ~/wardenrun-signing
umask 077
cat > cert.conf <<'EOF'
[req]
distinguished_name = dn
x509_extensions = ext
prompt = no
[dn]
CN = wardenrun release signing
[ext]
basicConstraints = critical, CA:false
keyUsage = critical, digitalSignature
extendedKeyUsage = critical, codeSigning
EOF
/usr/bin/openssl req -x509 -newkey rsa:3072 -nodes -days 3650 -config cert.conf \
    -keyout key.pem -out cert.pem
```

Make the PKCS#12 file with the **system** `openssl` (LibreSSL, `/usr/bin/openssl`): its output
is what `security import` reads. The password is long and random; keep it in your password
manager.

```sh
P12_PASSWORD=$(/usr/bin/openssl rand -hex 24)
printf '%s\n' "$P12_PASSWORD"            # store it, then clear the terminal
/usr/bin/openssl pkcs12 -export -inkey key.pem -in cert.pem -out wardenrun-release.p12 \
    -passout env:P12_PASSWORD
```

If you only have OpenSSL 3 (for example from Homebrew), macOS cannot read its default PKCS#12
encryption: add the legacy algorithms, either `-legacy` or
`-keypbe PBE-SHA1-3DES -certpbe PBE-SHA1-3DES -macalg sha1`. An import that fails with "wrong
password" although the password is right is this problem.

Read the SHA-1 of the certificate (lower-case hex, 40 characters). This is the value that is
published and pinned:

```sh
/usr/bin/openssl x509 -in cert.pem -noout -fingerprint -sha1 | sed 's/.*=//; s/://g' | tr 'A-F' 'a-f'
```

Set the three secrets of the repository (Settings, Secrets and variables, Actions), or with
`gh` from your own machine:

| Secret | Value |
|--------|-------|
| `SIGNING_CERT_P12_BASE64` | `base64 -i wardenrun-release.p12` (the whole output) |
| `SIGNING_CERT_PASSWORD` | the PKCS#12 password |
| `TAP_TOKEN` | a fine-grained personal access token with **Contents: read and write** on the tap repository `homebrew-tap` and nothing else. Without it the tap job ends with a notice and the release still happens. |

```sh
base64 -i wardenrun-release.p12 | gh secret set SIGNING_CERT_P12_BASE64
gh secret set SIGNING_CERT_PASSWORD          # paste the password at the prompt
gh secret set TAP_TOKEN                      # paste the token at the prompt
```

The tap is an ordinary public repository named `mateuszgachowski/homebrew-tap` (Homebrew's
naming: `brew tap mateuszgachowski/tap`). Create it once, empty or with a README; the workflow
adds `Formula/wardenrun.rb`.

**Backup and cleanup.** Keep exactly one offline backup of `wardenrun-release.p12` and its
password, somewhere that is not this Mac's disk alone (an encrypted disk image on a drive in a
drawer, or a password manager's secure attachment). Then delete `key.pem` and the folder's
temporary files. Never commit any of this: the repository's `.gitignore` is not a defence, the
folder simply must not be inside it. Never paste the key or the password into an issue, a chat
or a log.

Two properties worth knowing:

- The certificate is **not trusted by macOS** (self-signed). That is fine: `codesign` signs with
  it by hash, and the keychain item is bound to the signature's requirement, not to a trust
  chain. `import-signing-cert.sh` tries to mark it trusted for code signing and only notes a
  refusal.
- It is valid for ten years. Whether an expired certificate still opens existing keychain items
  has not been tested: plan a rotation (section 6) well before the ten years are over.

## 2. Cutting a release

Prerequisite: the manual checklist of section 3 passed on the commit you are about to tag.

1. **Make the release commit.** In `Sources/WardenrunCore/Usage.swift` change
   `WardenrunVersion.current` from `0.1.0-dev` to the release version (for example `0.1.0`).
   Commit it on `main` through a pull request like any change.
2. **Tag that commit** and push the tag (the tag must be `v` plus exactly that version):

   ```sh
   git tag -a v0.1.0 -m "wardenrun 0.1.0"
   git push origin v0.1.0
   ```

3. **Watch the run** (Actions, "release"). What each job does and where it stops:

   | Job | What it does | It stops (and nothing is published) when |
   |-----|--------------|------------------------------------------|
   | `build` (macOS) | checks the tag equals `WardenrunVersion.current`; `swift test`; imports the certificate into a temporary keychain; builds a universal binary, signs it with the hardened runtime; verifies the binary inside the tarball (signature, hardened runtime, no `get-task-allow`, both architectures, designated requirement names exactly this certificate, reports the version); uploads tarball and checksum; deletes the keychain, always | the tag differs from the source, a test fails, the certificate cannot be imported, any check of the binary fails |
   | `release` (Ubuntu) | re-checks the checksum, attests the build provenance of the tarball (GitHub artifact attestation), creates the GitHub release with tarball, `.sha256` and notes that contain the certificate SHA-1 | `build` did not finish clean; a release for that tag already exists |
   | `tap` (Ubuntu) | renders the formula from `packaging/wardenrun.rb.in` and pushes it to the tap | (skipped with a notice when `TAP_TOKEN` is empty) |
   | `verify-install` (macOS) | `brew tap`, `brew install`, `codesign` requirement contains the certificate SHA-1, `brew test`, `wardenrun version`, `wardenrun doctor` shows `ok` for `hardened-runtime` (a runner has no screen session, so other lines may fail) | **fails after publishing**: see section 5 |

4. **Bump the development version** back (for example `0.1.1-dev`) in a follow-up pull request,
   so a build from `main` never claims to be the release.

A tag is never reused. If a release has to be redone, delete it (section 5) and tag the next
version.

## 3. Manual checklist before tagging

The Touch ID flows cannot run on a CI runner. Run these on a real Mac with a fingerprint
sensor, with a **release build signed with the real certificate** (`scripts/package-release.sh`
with `SIGN_IDENTITY` set, or the artifact of a dry-run tag in a fork), against a real Vaultwarden
and the dedicated account. Tick each line; any failure stops the release.

- [ ] `wardenrun doctor`: every line `ok` (the `bw` version may say `untested`), `certificate`
      shows the SHA-1 from section 1.
- [ ] `wardenrun setup` from a terminal: the sheet text names the pinned `bw` and the server,
      a touch completes it, no keychain dialog appears.
- [ ] `wardenrun run <item> --env TOKEN=password -- sh -c 'echo "$TOKEN"'`: the sheet shows the
      full command and `as $TOKEN`; a touch runs it; the output shows `[REDACTED:<item>]`.
- [ ] The same with `--stdin password` and with `--file KEYFILE=password`; the temporary folder
      `wardenrun-*` is gone afterwards.
- [ ] Masking of an encoded value: `... -- sh -c 'echo "$TOKEN" | base64'` prints a redacted
      marker, not the encoding.
- [ ] Say **no** on the sheet: exit 77, no `finished` line in the audit log. Let it **time out**
      (60 s): exit 77.
- [ ] Say no three times in a row: the fourth attempt is refused at once (lock-out, 60 s).
- [ ] `Ctrl-C` during the Touch ID wait, during the `bw` phase (right after the touch) and while
      the command runs: no `bw serve` left (`pgrep -fl 'bw '`), no `wardenrun-*` folder left.
- [ ] `[exe changed]`: approve a script once, change the script, run again: the sheet carries
      the tag.
- [ ] `wardenrun run` over `ssh` (no screen session): exit 78 and nothing asked.
- [ ] `wardenrun new <name> --length 32`: one line, no password printed; the item exists in
      the dedicated collection; a second run with the same name fails before anything is created.
- [ ] **A binary signed by another certificate cannot read the keychain item.** Copy the
      binary, re-sign the copy ad hoc (`codesign --force --options runtime -s - ./copy`), run
      `./copy doctor`: `protected-item` is `FAIL`. macOS may show a keychain dialog: do not
      enter a password, choose Deny.
- [ ] **A fresh install keeps the signature.** On a Mac (or user account) that has never seen
      wardenrun: `brew install mateuszgachowski/tap/wardenrun`, then
      `codesign -d -r- "$(command -v wardenrun)"` contains the certificate SHA-1. Then, on the
      Mac where you ran the rest of this list, upgrade from the build you tested to the
      Homebrew one: `wardenrun doctor` still shows `protected-item` as `ok` (the upgrade case).

## 4. After the release exists

1. Put the certificate SHA-1 into [`README.md`](../README.md) ("Verify, don't trust") and
   [`SECURITY.md`](../SECURITY.md), replace "Not available yet" in the README by the real
   install command, and update the Status section. One pull request.
2. Check your own download the way users are told to:

   ```sh
   shasum -a 256 -c wardenrun-0.1.0-macos-universal.tar.gz.sha256
   gh attestation verify wardenrun-0.1.0-macos-universal.tar.gz --repo mateuszgachowski/wardenrun
   ```

3. Install from the tap on a clean machine once more (checklist, last item).

## 5. When `verify-install` fails

The release is public by then. A failure means a user who installs it may get a binary whose
signature is not the one the keychain item expects (for example Homebrew re-signed or patched
it). Do not announce the release.

1. Look at the log of the job: which check failed (`codesign` requirement, `brew test`, `doctor`).
2. **Yank the release** and its tag, and revert the tap commit:

   ```sh
   gh release delete v0.1.0 --cleanup-tag --yes
   git clone git@github.com:mateuszgachowski/homebrew-tap.git && cd homebrew-tap
   git revert --no-edit HEAD && git push origin HEAD
   ```

3. Fix the cause (formula, `skip_clean`, install step), run the dry run and the manual
   checklist again, then cut a **new** tag (`v0.1.1`). Never move or reuse a tag.

If `build` or `release` fails, nothing is public: fix, delete the tag locally and on the remote
(`git push --delete origin vX.Y.Z`), and tag again.

## 6. After a leak: rotation

When the signing key may have leaked, or a release that should not exist was published:

1. Delete the three secrets, delete the compromised release (`gh release delete`), and publish a
   security advisory that names the old certificate SHA-1 as revoked (also in `SECURITY.md`).
2. Generate a new certificate (section 1), set the secrets, cut a new release signed with it.
3. Users run `wardenrun setup` again: the keychain item of the old signer cannot be read by the
   new binary, by design. They check the new SHA-1 against `SECURITY.md`.
4. Update the SHA-1 in the README and `SECURITY.md`, and record what happened in the advisory.
